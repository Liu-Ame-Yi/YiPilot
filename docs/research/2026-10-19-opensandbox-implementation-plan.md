## 1. 目标与现状

目标是完整替换旧沙箱执行链路，同时收拢重复的编排和检查。推荐采用已调研的 B 路线：**本地保留业务、模型、审批和主 Git 工作区；服务器承担隔离执行与结果收集**。终态只保留 OpenSandbox 一个正式沙箱后端；历史记录仍可读，不长期维护双后端。

| 已完成 | 仍未完成 |
| --- | --- |
| 华为云 SSH 密钥登录；Docker、OpenSandbox Server/SDK 1.1.1；单个受信沙箱的命令、文件、限额与销毁检查 | 与旧执行合同等价的隔离 profile；Runner；本地远程调用；应用、验证、恢复和结果合同迁移 |
| 私有 GitHub 仓库与服务器只读拉取；首次同步提交为 `e01352fe6265280a77a18e014dd261daefd214c3` | 新服务发布、数据库迁移、端到端与并发验收 |
| 首次推送 CI 的 Lint 和 Type check 通过 | Test 在收集阶段发生 8 个 `ModuleNotFoundError: No module named 'tests'`，不能声称全量通过 |

服务器为 2 vCPU、2 GiB 标称内存、40 GiB 盘、2 Mbps 出网。安装后一次空闲采样的可用内存约 1051 MiB；它不是运行峰值或后续容量保证。[安装证据](2026-10-19-opensandbox-server-installation.md)、[同步记录](2026-10-19-yipilot-github-sync.md)、[失败 CI](https://github.com/Liu-Ame-Yi/YiPilot/actions/runs/39251379858)。

## 2. 调用方式与职责

```text
本地 YiPilot
  业务、模型、审批、Git、输入冻结、结果校验/应用
          │ HTTP：提交、查询、取消、读取日志、下载结果
          │ 开发期经 SSH 隧道；Runner 仅监听服务器回环
          ▼
服务器 ExecutionRunner（同一仓库，一个进程）
  SQLite Job 记录、输入/工作/产物目录、预算队列、生命周期与恢复
          │ OpenSandbox SDK；管理密钥只留服务器
          ▼
OpenSandbox Server → Docker 沙箱
```

- 本地通过已有 `httpx` 调 Runner；本地工作流不直接操作 OpenSandbox、Docker、远端路径或卷。SSH 负责通道和运维，不另建远程文件管理协议。
- Runner 从首版启用独立客户端认证，提交/查询/取消/日志/下载均校验；本地凭据复用 SecretStore，服务器配置限制文件权限。该凭据与 OpenSandbox 管理密钥分开，均不进入任务环境、源码包和日志。单用户首版不扩展账户平台。
- Runner 拥有一次 Job 的执行事实；本地 Run 拥有业务意图与审批。两端不各维护一套完整业务状态机。审批在本地绑定冻结的输入、镜像、策略和预算；服务器只接受其允许的执行 profile。
- Runner 对自己登记的沙箱、可能存在的 sidecar 和目录负责，实际停止全部写入者后，才可信扫描并发布任务不可写的产物。不能把 SDK 返回成功当作已停止、已清理或业务检查通过。
- GitHub 分发程序版本；每次任务的输入快照和结果走 Runner。服务器拉取 YiPilot 代码不等于获得用户项目的当前输入。
- 本地断线后，服务器上已耐久接受的 Job 可以继续；后续模型、审批和业务步骤仍要等本地恢复。此方案不承诺本机关机后整条研发流程继续运行。

拟议最小接口为 `POST /v1/jobs`、`GET /v1/jobs/{id}`、`GET /v1/jobs/{id}/events`、`POST /v1/jobs/{id}/cancel`、`GET /v1/jobs/{id}/result`。它们尚未实现，不是当前可调用的命令或接口。

同一请求 key 与内容摘要绑定：重复提交相同内容返回同一 Job，内容不同则冲突。输入包先验证并完整发布，再事务记录接受；接受前不执行。创建/执行的远端副作用不能假定 exactly-once，未知结果不得自动重放。

## 3. 四个阶段与放行条件

### 第一阶段：修基线并验证隔离

工作顺序：

1. 在干净检出和 CI 相同入口复现 `tests` 导入问题，修正测试导入/入口配置，保持测试语义；检查本地与 CI 差异。先恢复离线测试可收集，再确认全套基线结果，不把已有失败归到迁移头上。
2. 固定当前 Server/SDK、官方 BOM 的 execd 与任务镜像 digest；用独立 Python >=3.11 环境准备未来 Runner，保留系统 Python 3.10 和现有 OpenSandbox 环境。
3. 逐项验证任务身份、只读 rootfs/受控临时目录、仅 Job 工作目录可写、禁出网、资源与日志限额。当前 POC 仍是 root、rootfs 可写和未 deny 出网，正式代码不得直接进入。
4. 从任务内测试跨 Job、宿主/内网/metadata、管理入口及控制凭据是否可达；覆盖已有调研中的初始化入口/执行身份问题。只限制监听地址不足以证明任务内隔离。
5. 通过可信运行时观察核验 UID、挂载、capabilities、no-new-privileges、CPU/内存/PID、swap、网络，以及退出/取消后的真实残留；只清理有明确归属的测试资源。

**交付：** 代码测试基线报告、版本/镜像清单、隔离差异与每项探针结果。

**G1：** 未解决的安全差异明确阻止不可信工作负载。先验证上游配置/受控镜像能解决多少；确实缺能力时，评估最小固定补丁及升级回归成本，再决定实施方式，不能默认复制早期计划中的整套 fork。若维护成本过高，回到接入方案取舍，不先重写业务来锁定投入。

### 第二阶段：实现一个完整远程 Job

先使用仓库内自有、无敏感信息的 Python 小样例，不调用真实模型、不应用到用户正式工作区。

1. 定义版本化执行请求/结果，绑定 Task/Run、请求 key、输入 digest、注册 argv、profile、镜像与预算。远端不接收任意宿主路径、shell 或 Docker 参数。
2. Runner 用一个 SQLite 保存 Job 和 attempt；受限目录根下区分不可变 `input`、任务可写 `work`、可信发布 `artifacts`。文件和 SQLite 分步提交、可恢复，不声称它们有跨介质原子事务。
3. 本地冻结快照并有界上传；Runner 验证路径、链接/特殊文件、数量、单文件/总量、摘要和展开后大小，完整接受后才创建沙箱。
4. 执行后真实停止并核验写入者，再扫描完整文件清单。结果包含退出事实、日志、输入/输出 digest、Git mode、增改字节和明确删除项，原子发布到任务不可写的产物区。
5. 本地下载到安全 staging，用原来冻结的输入重建结果并重新计算完整清单；不能从已经变化的用户工作目录补未修改文件。输出校验失败不得进入 diff/应用。
6. 分别约束命令、停止/清理、上传/下载和日志期限；HTTP 断线不触发重跑，取消请求收到不代表停止完成。

**交付：** 一个“本地提交 → 服务器运行 → 可信收集 → 本地完整性校验”的可复现样例；本地与服务器可用同一 Job ID 查证结果。

**G2：** 正常、非零退出、修改/新增/删除文件、字节与 Git mode 往返均正确；缺包、摘要不符和越界路径被拒绝。这一阶段只证明新链路，不宣称所有 YiPilot 调用已经替换。

### 第三阶段：并发、断线和崩溃验收

1. 基于真实 Runner，依次测 1、2、4 个活跃沙箱；记录主机/容器内存峰值、OOM、耗时、控制面响应、磁盘、吞吐和清理残留。压力上限以不挤爆宿主为准，准入不足时排队。
2. 四个是本机轻量任务的容量目标，不是所有任务的保证。调度同时检查槽位、资源预算和磁盘；pytest/Ruff/mypy 等子执行共用全局额度。既有约 1 GiB 的验证预算不能偷偷降小以凑并发。
3. 项目锁缩短随第四阶段实际调用迁移一并交付，避免在旧业务尚未替换时破坏其执行所有权。目标是远程等待不占整个项目锁；同仓库任务使用独立快照，同一目标的最终应用串行并重新核对基线，迁移/配置仍协调排空。Runner 的四并发不等于同项目业务已并发。
4. 注入重复提交、提交响应丢失、本地断线、Runner 重启、超时、取消、扫描/下载中断、销毁失败；核对同一请求不重复执行，未知结局不自动重放，清理未完成不错误归还额度。
5. Runner 重启先对账自己已登记的 attempt 与运行时；结果不确定时停止并显式记录 uncertain。准确回收过期 Job 产物，不做全局 Docker prune。

**交付：** 本服务器可启用的实际并发/profile 表、故障结果与恢复记录。

**G3：** 活跃沙箱数和资源预算不超额；通过的并发档位有真实数据；断线不丢 Job，重启不重复命令，取消后无活跃写入者，失去完整证据时明确失败。未通过四并发时保留可用低档，不把排队数称为运行并发。

### 第四阶段：迁移全部调用并删除旧运行实现

1. 在 `ProjectApplication` 统一装配 RunnerClient；迁移应用、验证、有限 repair、恢复、doctor 与全部 CLI 调用，清除上层 Docker 细节和重复生命周期编排。同时将长项目锁改为 Run/Job 所有权和共享写入/最终应用的短临界区，保留基线重查和迁移排空。
2. 将本地 Docker inspect 证据依赖改为版本化远程执行事实与本地字节校验；保留审批、源码限制、diff 和可信 Git 应用能力。不伪造旧 Windows backend、`network=none` 或 Docker container ID 来凑 v1 schema。
3. 历史 v1 记录只读可查；新请求使用新合同与审批指纹，旧审批不能授权新 profile。避免直接改 `SandboxAssociation` 而连带重写所有 SourceManifest；为新增持久化字段做真实版本迁移和备份/失败检查。
4. 更新相关 fixtures、架构约束与测试；删除旧 `DockerSandboxWorker` 的实时执行、无调用包装和失效分支。保留仍为 Git/可信本地工具服务的 `LocalCommandRunner`。
5. 本地测试和 CI 通过后推送，服务器拉取确切 SHA、安装锁定依赖并部署 Runner。更新前排空任务、备份需要迁移的本地/远端数据；更新后先跑健康和小样例，再做真实业务演练。

**交付：** 唯一正式执行路径、删除/保留清单、真实使用说明、绑定提交和 profile 的端到端证据。

**G4：** 离线测试、Linux Runner 测试及真实远程集成检查通过；拒绝/过期审批不执行，应用/验证/repair 的结果绑定正确，用户主工作区不被越权覆盖。旧 Docker 执行路径在最终版本无调用方，历史记录仍可读。

开发中的阶段提交用于审阅和验证；正式切换发生在 G4 通过后，不在生产长期双跑。失败可切回先前完整程序/环境，数据恢复按备份与 schema 兼容规则执行；不通过自动切后端或自动重放来“恢复”未知任务。

新增职责只有本地 RunnerClient 和远端执行模块；不预设文件数，不为每个方法创建一层包装。共享校验复用现有纯逻辑；不把受信宿主执行器和沙箱执行强塞入不合适的旧 `ExecutorPort`。

检查总代码和故障路径的变化，不能只统计删掉 DockerWorker 的行数。新 Runner 必须实际消化队列、停止、扫描、恢复等复杂度，而非只转发 SDK。

## 5. 首版资源与运维安排

- 一个 Runner 进程、一个 Job SQLite、一个目录根、有限并发。SDK/运行时观察只放服务器；不增加 Redis、Celery、对象存储、预热池、多租户或 Kubernetes。
- 当前机器先完成开发与轻量验收；是否升级由峰值与等待数据决定。最多四个轻任务的目标不取消预算准入；重构建/完整验证可排队，资源不足明确报错。
- 使用预制、固定 digest 的 Python 工具镜像，尽量在本地/CI 构建。任务期间不临时放开出网安装依赖；缺依赖按镜像/profile 变更重新验证。
- 2 Mbps 出网下，每 Job 传完整清单和增改字节，避免回传全部未改文件；不引入跨 Job 增量同步或 CAS。日志有界，传输期限按包大小单独安排。
- 开发期 Runner 与 OpenSandbox 保持回环监听，使用已有 SSH 通道和 Runner 独立认证；不要求用户新增公网管理端口。以后独立公网使用时再增加 HTTPS，并复验访问授权与暴露范围。
- K8s 为后续专项，需要重新设计存储、可信采集和清理；本轮不承诺只改 endpoint 就可迁移。
