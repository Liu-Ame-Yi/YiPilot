# OpenSandbox 第三阶段：恢复、保留与真实并发

日期：2026-10-20（Asia/Shanghai）。状态：**Runner 受信样例通过，正式业务尚未切换。** 在第二阶段闭环上补齐创建归属、硬磁盘上限和负载保留，并完成华为云主机上的 1/2/4 轻任务及选定故障测试。[结构化证据](evidence/2026-10-20-opensandbox-reliability.json)、[实际部署合同](../../deploy/runner/README.md)。

## 修改范围

| 位置 | 实际行为 |
| --- | --- |
| Runner store/domain/HTTP | SQLite v1→v2 事务迁移；过期状态可查询，结果返回 410，去重 key 不释放 |
| Runner service | 默认 24 小时/32 份负载；只回收本 Runner 已登记的终态任务；下载保护、崩溃后继续删除；输入和采集共用大字节临界区 |
| Runner runtime / 固定 Server 补丁 | 创建前持久登记确定的 UUID；宿主租约只消费一次，实际创建线程持锁至结束；回收撤销租约，拒绝迟到请求 |
| Runner disk | 每 Job 一个 256 MiB 稀疏 ext4 loop 文件系统；UUID、设备和镜像核验；正常卸载成功后才归还额度 |
| Runtime cleanup | API 故障或 sidecar-only 时，仅按归属核验过的 Docker ID 回收；缺证据、存留写入者或卸载失败均保持隔离 |
| 验收 | 复用冻结包、HTTP 客户端与可信重建；新增根用户专用的受信可靠性脚本，不增加任务队列或中间服务 |

资源身份仍属于固定 yipilot-python-v2，任务 UID/GID 10001、零 capabilities、受保护控制面、只读 rootfs 和禁出网边界不变。创建租约是新增的宿主协议，必须排空后与 Runner 一起更新；原上游安装包和 8080 配置未修改。重新跑过 18 项隔离检查和控制进程故障检查。

数据库升级前使用 SQLite backup 备份。首次迁移为旧终态记录设置当前保留起点，避免升级即删除全部历史。到期先落盘轻量去重记录，再删负载，删除中断可重启继续；未登记目录不自动清理。去重表随总请求量增长，不能把它称为永久固定空间。

## 容量实测

主机标称 2 核/2 GiB，实际 MemTotal 约 1771 MiB，无 swap。默认准入改为总内存 768 MiB、CPU 1500m、最多四槽和 4 GiB 空盘保留。每个 128 MiB/250m 请求再计入 sidecar 64 MiB/100m，四任务合计 768 MiB/1400m；超预算单任务明确拒绝，不缩减已批准请求。

固定样例每个分配 48 MiB，写开始标记，等待 12 秒再写完成标记；以开始与完成区间核对实际重叠，分别采样主容器、sidecar、Runner RSS、主机 MemAvailable、OOM 及健康响应。每轮都停止写入者、核对资源、重建并验证结果后结束计时。

| 请求数 / 实际重叠数 | 整批耗时 | 主机最低可用内存 | 单主容器峰值上限 | 单 sidecar 峰值上限 | OOM |
| --- | --- | --- | --- | --- | --- |
| 1 / 1 | 17.07 s | 794 MiB | 61.8 MiB | 5.6 MiB | 0 |
| 2 / 2 | 17.06 s | 715 MiB | 62.0 MiB | 5.8 MiB | 0 |
| 4 / 4 | 18.51 s | 566 MiB | 62.1 MiB | 7.1 MiB | 0 |

最终四并发轮 Runner RSS 峰值约 66.5 MiB，回环健康响应最长约 7.9 ms。观测使用 cgroup v2 的 memory.peak（不支持时取 memory.current 的采样峰值）。每轮结束无容器、runtime volume 或 work 挂载残留；相同样例的前轮也达到四重叠，故障修复后重新验收最终候选。

**结论只覆盖这个轻量负载。** 并发测量在服务器内发起 HTTP、校验结果，未测公网大包吞吐、持续高 CPU、完整 pytest/Ruff/mypy 或重构建。现有业务 1 GiB 验证请求未被改小；在 768 MiB 总预算下会拒绝，需另行校准可承载配置。不能把四槽推广为任意四个任务，也不能据此承诺同项目业务工作流并行。

## 故障与恢复

| 实际注入 | 验收事实 |
| --- | --- |
| 工作目录写满 | 独立文件系统返回 ENOSPC；样例捕获后删除填充文件，仍能可信收集并卸载；未写满宿主盘 |
| 提交响应丢失 | 完整发送后关闭连接，重提冻结包返回同一 Job，未创建新 attempt |
| 上传/下载中断 | 不完整上传不被接受；中断下载后可从同一冻结输入重新下载校验 |
| 真 SSH 隧道断开 | 本机在远端脚本运行中终止 SSH 进程，重新建立隧道后取回同一 Job，调用标记仅一条 |
| Runner SIGKILL | 实际命令运行中强制终止；systemd 重启先停止和对账，结局 uncertain，同 key 不重放 |
| work 卸载失败 | 只用可信辅助进程占住该样例 cwd，正常卸载失败后保持 cleanup_failed；后续任务排队，结果不可下载；解除占用后重启恢复 |
| 控制 API 暂停 | 暂停候选 Server，取消运行中任务；删除 API 快速失败后由宿主按核验过的 ID 回收，资源和挂载清零 |
| 创建响应丢失 | 先耐久记录并发出真实创建请求，不读取响应，重启 Runner；清理同一 UUID，记录 uncertain，再发迟到创建请求被拒绝 |
| 到期回收后重启 | 只将自有样例的完成时间置为过期，实际服务重启执行 GC；状态 result_expired、结果 410，原请求仍绑定同一 Job |

首次 API 暂停测试暴露了删除路径的 SDK 默认重试等待问题，没有把失败报告算成通过。通过协程和实际 Runner 复现确认删除阶段等待后，改为 5 秒 HTTP 超时、关闭该操作重试，并保留外层删除/关闭期限；最终候选重新跑过上述矩阵。

Server 若在实际 Docker 创建中死亡，文件锁释放并不证明已发给 Docker daemon 的操作全部结束。新增 settled 完成证明；缺失时保存 revoked_unsettled 并保留预算。这个失证分支通过单元测试证明跨两次回收仍不释放；没有声称本轮已经实测 Server/Docker daemon 在任意指令处同时崩溃，或自动恢复全部未知结局。

## 检查、发布与下一步

本地受影响测试 132 passed、2 skipped（POSIX 租约和真实上游构建由 Linux CI 验证）；Ruff 通过，mypy 81 个源文件通过。完整 Windows 离线测试、Linux Runner 和真实固定补丁构建，以本提交三项 CI 为准。结构化证据绑定候选安装字节、部署资产、锁定依赖和自有 Job；服务器最终检出绑定 CI 的确切提交，安装包逐文件核对。

验收后 Runner/profile 停止且 disabled，原 8080 保持健康，容器、卷和任务挂载清零。未调用真实模型、未操作用户项目主工作区，也未放行正式不可信任务。
