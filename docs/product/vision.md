# 产品定义与完整流程

状态：**已确认的产品范围；完整流程尚未实现。** 更新：2026-09-07。

Yipilot 是本地运行、面向单个 Python 仓库的自动研发交付控制器。用户提供仓库目录、需求和必要授权，系统整理需求、设计、评审、编码、验证并交付可审阅的 PR/MR。它不自动合并，也不等待人工合并来结束任务。

## 输入与文档职责

| 输入/产物 | 内容与责任 |
| --- | --- |
| 仓库 | 单个 Git 仓库及目标分支；提供已有代码、测试和实现约束 |
| 原始需求 | 直接文本或 PRD；第一版支持本地 Markdown/TXT，可同时提供参考材料 |
| PRD | 产品需求文档：背景、目标、用户场景、范围、行为与产品约束；不要求用户先写完整 PRD |
| SRS | 软件需求规格：明确行为、边界、约束、验收标准及需求出处；是下游执行的需求基线 |
| SDD | 技术设计：结合代码现状明确模块、接口、数据、改动步骤、风险和测试映射 |

原始材料单独留存，标明本次要求、背景参考或现状证据。模型建议不能伪装成用户要求；用户本次明确说明优先于历史材料。已有代码用于理解现状，不自动覆盖产品目标。

## 输入、输出与放行

| 阶段 | 输入 | 输出及放行条件 |
| --- | --- | --- |
| 准备 | 仓库、需求材料、模型/执行配置、授权范围 | 来源快照、代码基线、隔离工作区；环境和权限可用 |
| 需求整理 | 材料与相关代码事实 | SRS，含范围、非目标和验收标准 |
| 需求评审 | SRS 与原始证据 | 需求评审报告；阻塞歧义、冲突和关键遗漏已处理，否则修订或澄清 |
| 技术设计 | 通过评审的 SRS 与仓库 | SDD，包含实现与验证方案 |
| 设计评审 | SRS、SDD、代码证据 | 设计评审报告；无阻塞问题，否则修订 |
| 实现 | 已接受文档与隔离工作区 | 代码、测试、差异和执行证据；改动不越界 |
| 验证与代码评审 | 同一代码版本、需求与设计 | 测试/静态检查/评审结果；失败可有限次修复并重验重审 |
| 发布 | 通过检查的候选与发布授权 | 提交、远端任务分支、PR/MR 及其确认记录 |
| CI 与交接 | 当前提交、已配置检查 | 当前提交的 CI 结果、交接报告；必需检查通过才能 review_ready |

CI/Jenkins 是可选集成；没有配置时记录 not_configured，不声称 CI 已通过。已配置的必需检查缺失、失败或未知不能算通过。代码导致的 CI 失败可有限次修复，基础设施故障按重试预算处理。

交接报告包含 PR/MR、提交 SHA、需求完成情况、文档与验证证据、已知限制。后续审核和合并交给代码托管平台与团队流程。

## 人工何时介入

| 情况 | 处理 |
| --- | --- |
| 首次使用 | 提供模型/仓库/执行环境配置与授权范围，可复用已保存配置 |
| 关键需求歧义或材料冲突 | 集中提出必要问题，保存等待项；答案绑定需求版本后恢复 |
| 需要扩大权限或数据发送范围 | 暂停相应动作，请求明确授权；模型不能修改策略 |
| 缺少必要材料、环境无法恢复、预算或修复次数耗尽 | 保存证据和原因，等待用户补充、调整或结束 |
| 项目明确要求某阶段人审 | 保存待审结果，按该阶段规则等待 |
| 普通技术选择、授权内读写测试、预算内返工 | 自动执行，不逐步骤请求批准 |

需求变化使相关设计/评审失效；代码变化使相关验证/代码评审失效。恢复必须核对输入和证据版本，不能拿旧通过结果放行新版本。

## 缺陷修复与范围

修复 Bug 是普通研发任务：SRS 记录实际/预期行为及复现条件，SDD 记录诊断与修复方案，验证优先提供修复前失败、修复后通过的回归证据。无法复现时记录不确定性，不假称已确认根因。小任务文档可以短，但不能省略目标、影响范围和验证依据。

当前不建设独立 Bugfix 子系统、多仓库任务、自动合并、服务端、多租户或分布式 worker。外部网页/Issue/企业文档/MCP 来源按实际需要接入，复用相同的需求处理流程。

技术方案见 [V2 架构](../superpowers/specs/2026-09-07-yipilot-v2-architecture.md)；实际已有能力见 [当前状态](status.md)。产品范围已明确不代表技术提案已实现。
